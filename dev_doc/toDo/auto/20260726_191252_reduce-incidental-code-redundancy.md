# 持续清理偶遇的代码冗余

## 背景

- 当前 yadof 主要由 AI 生成和持续修改。AI 容易通过叠加分支、包装层、兼容入口、
  防御性判断和辅助函数来完成新要求，却较少主动删除已经失去价值的实现，因而代码量
  可能只增不减。
- 本次抽样浏览了 `evaluate_manager/condor_runner.py`、
  `evaluate_manager/api.py`、`surrogate/runtime.py`、`job_template/` 以及
  `tools/view_cost.py`、`tools/view_time.py` 和相应测试。样本中既存在可能合并的重复
  元数据整理和绘图配置，也存在看似重复、实为公共 API 或故障隔离契约的代码。
- 因此，清理不能只追求行数减少；必须先证明某段代码没有独立职责，再进行小而可验证
  的简化。

## 目标

- 在日常修改自然接触到代码时，顺带识别并清理范围内已经可以确认的冗余。
- 在保持公共 API、数据格式、错误语义、并发行为、平台差异和任务/框架边界不变的
  前提下，减少重复实现、不必要的间接层和无效防御代码。
- 让每次清理都容易审查、容易验证、容易回退，并逐步扭转“每次修改只增加代码”的
  倾向。

## 指导

### 触发和范围

- 只在正常任务已经使某个文件进入当前工作范围，并自然暴露出冗余时触发。不要仅为了
  本 toDo 主动扫描整个仓库，也不要把用户当前任务扩展成全项目重构。
- 每次只处理一个边界清楚的冗余问题，最多修改一至两个文件。测试、文档和配置文件也
  计入这个数量；通常优先采用“一个实现文件加一个直接相关测试文件”的组合。
- 如果完整改动需要三个或更多文件，先停在可独立验证的边界；把剩余候选和拆分建议
  写入汇报，不要在同一次触发中铺开。
- 不要把同一文件中彼此无关的多个清理项捆绑成一次修改。

### 先证明冗余

- 在删除或合并前，检查直接调用点、导入和导出、相关测试及当前文档。动态加载、CLI
  路由、资源复制和插件式入口不能仅凭静态搜索没有命中就判定为未使用。
- 优先关注：
  - 语义和错误行为都相同的重复分支、转换、常量或辅助函数；
  - 已被统一实现取代的旧路径、无效回退和不可达分支；
  - 只做参数原样转发、却没有稳定边界价值的包装层；
  - 同一数据被反复校验、复制或转换，且中间结果没有独立契约；
  - 重述代码本身、已经失真的注释和 docstring；
  - 重复覆盖同一行为、没有增加边界或回归价值的测试代码。
- 以下内容即使形式相似，也不能直接视为冗余：已公开的 API 别名、兼容承诺、不同失败
  阶段的隔离逻辑、原子持久化和锁、超时及资源回收、不同平台或执行后端的差异、任务
  代码与框架代码的职责边界。没有足够证据时保留并汇报。

### 简化原则

- 优先选择删除无效代码、合并完全相同的分支、直接复用已有实现或缩短局部数据流。
  不要先创建新的通用层。
- 只有当至少两个真实调用方共享同一语义和变更原因，而且提取后能降低总代码量或认知
  负担时，才增加共享辅助函数。不要为了消除表面相似而制造新的 `utils`、转发函数或
  配置对象。
- 清理应保持可观察行为不变。若发现的是缺陷、API 变更或架构调整，应作为独立任务
  汇报，不能伪装成冗余清理。
- 保持 yadof 的现有边界：跨任务不变的机制属于 package；随优化任务变化的行为属于
  workspace；分布式 workflow 不得依赖 execute 节点导入 yadof。
- 净代码行减少是有用信号，但不是唯一成功标准。不能通过压缩可读性、合并不同职责、
  删除必要断言或降低诊断质量来换取更小的行数。

### 验证和汇报

- 运行与改动最接近的测试，并按风险补充必要的静态检查或更高层测试。不要因为是
  “清理”就跳过验证。
- 每次完成后必须用简短文字汇报：
  - 修改了哪一至两个文件；
  - 识别出的冗余是什么，以及为何可以安全删除或合并；
  - 代码大致增加和删除了多少，最终是否净减少；
  - 运行了哪些验证及其结果；
  - 仍保留了哪些可疑部分，以及保留原因。
- 如果没有足够证据完成安全清理，也要简要说明候选位置、风险和未修改原因；不要为了
  产生 diff 而勉强改动。

## Completion Rule（完成规则）

- 对一次自然触发而言：一个明确的冗余点已经在一至两个文件内完成清理，相关行为得到
  验证，并已按上述格式进行文字汇报。
- 本 toDo 是持续性的；单次清理完成后仍保留，供以后在其他正常任务中遇到冗余时继续
  使用。
